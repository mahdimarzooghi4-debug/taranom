**Date:** 2026-10-11. **Scope owner:** user instruction to accelerate implementable product capability packages while preserving approved Business/Technical scope and independent gates. **Parent:** Sprint62 PR #70, exact-head Push+PR CI 13/13 green and preliminary COMMENT-only Code Review. **Authoritative decisions:** TRN-BIZ-015/016/017/024, TRN-TECH-005 .NET domain owner, TRN-TECH-012 no real member session or BFF authorization; TRN-TECH-052 membership time boundaries; TRN-TECH-071 local-only HTTP dev host.

## User benefit in the bounded present

The member's **first waiting period** is exactly 90 complete 24-hour periods from a *separately evidenced official membership activation*; neither creation of an account, a paid transaction, a proofing result, nor calendar 'three months' starts it. The already existing and tested **domain-owner** \`MembershipWaitingPeriod.Observe\` contains the correct rule but was not connected to any real HTTP/browser interaction. To move actual implementation forward without inventing a real IdP, PSP, official activation evidence or financial entitlement, Sprint63 creates a deliberately **anonymous hypothetical educational calculator** exposed only by the existing .NET loopback technical host, not a member entitlement API.

## Contracts, protections and working functionality

- Add a project reference from the existing localhost-only \`Taranom.OperationsStatus\` web host to the canonical \`Taranom.MemberGovernance\` domain library. Do **not** rewrite the 90-day rule in JavaScript or invent new waiting thresholds.
- Add \`POST /internal/ops/v1/waiting-preview\` as an **anonymous, stateless, non-mutating hypothetical operation**. Only JSON \`{"activationUtc":null | "YYYY-MM-DDTHH:mm:ssZ","observedUtc":"YYYY-MM-DDTHH:mm:ssZ"}\` allowed. No member identifier, identity data, payment, clinician, organization, consent, wallet or token field. Exact two-property input and maximum 512 bytes even with chunked upload; strict UTC second-resolution Z suffix, nonempty explicit observed clock, no guessed server clock, bounded JSON depth; reject malformed/extraneous/cross-origin input with 400. It never persists or logs form values.
- Delegate **all temporal meaning** to \`MembershipWaitingPeriod.Observe\`: no activation -> \`OfficialActivationMissing\`; observation preceding activation -> \`ObservationBeforeActivation\`; 1 second short of 90 exact days -> \`StillWaiting\`; exactly 90 complete days -> \`NinetyFullDaysElapsed\`; threshold UTC only if safely derivable. Every 200 response is explicitly \`hypotheticalOnly=true\`, \`officialActivationVerified=false\`, \`memberEligibilityVerified=false\`, \`walletCreditAuthorized=false\`, \`nationalReleaseAllowed=false\`. Every 400 response also explicitly denies all rights and does not emit a fake 'success' state. Earlier \`GET /internal/ops/v1/status\` remains read-only; its mutation POST still 405, and all 17 official release blockers remain unchanged.
- Extend the live \`apps/ops-web\` React local console with a clear Persian RTL **educational** form (optional hypothetical activation timestamp + explicit UTC observation timestamp), real POST to the same-origin .NET host with credentials omitted/no-store, domain response validation, user-facing timing explanation, and failure/no-activation/short-of-threshold states. The UI never says the user's own account is active, the official event verified, or the wallet spendable. No browser persistence, member ID, actual enrollment, personal profile, medical data or external network call.
- Extend existing genuine local Python HTTP smoke with exact threshold, one-second boundary, missing activation, observation before start and malformed or extra-field/oversize denial; add five real Chromium browser/API tests to inherited five, plus all 12 other prior CI jobs, run complete exact-head Push/PR 13-job suites and fix regression failures before review.

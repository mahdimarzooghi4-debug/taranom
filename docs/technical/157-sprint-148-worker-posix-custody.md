# TRN-TECH-157 — Sprint 148: Linux UID separation for synthetic Worker evidence in isolated CI

**Scope:** remedy the prior limitation that Kestrel and HMAC verifier ran as the very same Unix user. This sprint exercises a distinct *unprivileged* Linux identity in the existing ephemeral CI full regression, with no approved Production service identity, custodian, network provider, clinical data, human review or operational topology.

The normal, non-root GitHub runner starts disposable Kestrel/.NET → local Python → SQLite synthetic Worker reads and produces the existing two-epoch SHA-256 evidence journal. Before the actual SIGTERM, a new `taranom_custody_qa` Linux system user (no home, no interactive shell) is created using the CI runner's known `sudo` privileges. It receives a **separate 0700 owned temp directory**, while the runner places a validated copy of *non-identifying synthetic-only evidence* in a 0755 shared staging directory with read-only 0444 file permissions. Through a minimal empty environment the unprivileged user runs the existing `worker_evidence_anchor.py create`; it generates a 0600 verifier-held key and HMAC manifest that the normal (non-sudo) Worker/runner UID cannot read. The same Linux custody account also cannot write the staged log.

After the existing real Kestrel restart and signed synthetic inventory recovery, the sender updates the staged evidence copy. The unprivileged custody identity independently verifies the exact pre-restart anchored prefix and Boot→Success extension, then exports a bounded ZIP + private receipt under its own 0700 folder. A root-mediated *test-only copy* transfers **only the public ZIP**, not the key or receipt, to a fresh custody-owned receiver folder. A separately invoked process running as the custody identity verifies that copy using the original private HMAC receipt. Finally the runner's unprivileged UID is tested for denial of read access to the private key and receipt.

The integration test fails closed if a POSIX user is not created, files are accessible to the wrong uid, wrong path/mode, missing or tampered evidence, unchanged or malformed Worker history, symlink, altered copy, or failed HMAC verification. The new AI unit tests verify CI-only guardrails and absolute path/mode rejection before any sudo command is considered. Existing 14 required jobs and original bridge/Chromium/Postgres/restored-journal tests remain intact. There are no new APIs, model inference/training, external AI SDKs, operational data or human decisions.

**Limitations:** this is **actual Linux discretionary access separation between two unprivileged processes**, NOT independent custody or legal attestation. The same CI runner has unrestricted `sudo` and hence can become root or the verifier uid and read or forge the HMAC key and receipt. Repository CI source controls both tests and roles; both are on one host and have no separate off-host retention, trusted timestamp, real signed institution identity, secrets vault, WORM archive, independently approved transport or real recipient. The key remains ephemeral and auditEvidence, independentCustody and productionReady stay `false`. Users must not infer Production readiness, authorization, human committee sign-off, consent or model promotion.

# TRN-TECH-182 — DRAFT / source-confirmed return of unverified Center follow-up to Member

Date: 2026-10-18. Basis TRN-BIZ-045 and TRN-BIZ-046: one member-facing path for complaint follow-up, but clinical/insurance/legal resolution remains exclusively with legally authorized providers and entities. Sprint 171 introduced member→center synthetic case handoff; this Sprint closes the reverse *technical communication* loop without inventing a notification provider or actor authority.

## Existing real source and bounded implementation
- Reuse the SAME existing CI-ephemeral localhost PostgreSQL support journal (`TRN-TECH-075`) and its read-only restricted reader, immutable event+paired audit, version CAS and no-authority flags. The GET `/internal/demo/v1/support/{caseRef}` already exposes each historical follow-up's persisted random UUID (`requestId`), noteRef, claimedActorRef and revision; no backend endpoint/schema/DB role is needed.
- In Center QA, only after a verified current snapshot with >=1 unverified follow-up and no pending write, issue a human-copyable JSON locator `TRN-TECH-182-TEST-FOLLOWUP-RETURN`, version 1, containing exactly: caseRef, synthetic memberRef, source topic, synthetic evidenceRef, original root request UUID, current support revision, latest follow-up request UUID, latest noteRef, latest claimedActorRef. The locator is derived from validated source only; it is never a real reply, authorization, clinical assignment, follow-up outcome, notification, legal decision or authenticated message. Changing selected case, reading genesis-only history or uncertain writes hides it.
- In Member Support, user must first manually type the exact `test:` caseRef and claimed memberRef, paste a bounded hand-carried locator, and explicitly click an independent **GET-only** confirmation. Reject malformed/missing/extra fields, unknown version, non-synthetic refs, unauthorized topic, invalid UUID, stale/wrong revision, wrong member/case, forged last-note and claimed actor. Independently re-read the exact support journal and verify all deny flags, root submission identity, exact **current revision**, complete ordered follow-up chain, and the **last persisted** follow-up's exact UUID+noteRef+actor. On failure clear displayed result rather than guess acceptance. A newer event makes the old receipt stale, not proof of an unchanged status.
- No automatic POST, provider contact, member message delivery, browser storage or share link with permissions. The payload is a locator for a *claim*, not evidence of medical treatment, insurance coverage, appointment, official complaint or legal service-level compliance. This component must never be exposed as authenticated Production member communication.

# TRN-TECH-153 — Sprint 144: fail-closed telemetry discontinuity across real Kestrel restarts

**Scope:** actually stop and start the synthetic CI-only Kestrel process with the existing .NET→Python one-shot read-only worker, without deploying a real AI service or choosing the Production IPC topology.

The previous Sprint 143 counters were process-local, non-durable, and reset on restart. This sprint makes that discontinuity *observable* rather than silently claiming continuous audit coverage. Each `AiWorkerQaCounters` instance mints an unpredictable 128-bit hex `instanceEpoch` when the host starts; it stays constant within the process, changes when a new host is initialized and **must never be used as a per-request metrics label, session identity, service authority, cryptographic proof of continuous uptime or a source of governance approval**. The telemetry response includes this standalone epoch and explicit fixed booleans `counterResetOnRestart=true`, `continuityAttested=false`. It continues to report `auditEvidence=false`, `operationalIdentityVerified=false`, `productionReady=false`, all authorization flags false, and only fixed, non-identifying in-memory counters.

**Real acceptance execution:** in the *existing mandatory* `ephemeral-center-workflow-full-stack` CI job, first run the entire inherited PostgreSQL, Kestrel/AI worker, Chromium and cross-portal regression; then persist only the non-sensitive 32-character epoch and two volatile counts in a private CI temp witness. The CI script sends SIGTERM to the actual Kestrel demo, waits for port closure, starts a new instance on the same isolated fixture, checks a changed epoch and ten reset counters, performs a genuine signed .NET→Python→SQLite synthetic inventory call and proves the new epoch has exactly one successful read with no false authority or hidden state carryover. The job then runs the existing isolated PostgreSQL recovery rehearsal unchanged. If the original Kestrel remains online or fails to restart, the test fails closed. An independent C# test verifies freshly constructed counters have a different epoch and zero values, while a single running counter instance keeps a stable epoch through 400 concurrent updates. Existing HTTP tests assert that epoch is stable during normal requests and that no user identity, worker HMAC or clinical data is exposed.

**Boundaries:** This is a discontinuity witness, **not a durable audit, recovery-point certification, process supervisor, uptime/continuity attestation, session management, controlled model restart or rollout**. The Python worker continues only read-only synthetic test-registry count retrieval; no model, patient record, consent, clinical/financial state, OIDC service identity or Production secrets are involved. Production transport/sandbox, accepted authority/grants, authorized datasets, model selection and accountable independent human promotion remain OPEN. Every stacked PR stays Draft/Open/Unmerged. No Ready for Review, Merge, Stage, QA Gate, Release, Production or nationwide activation; `DENIED_BY_DEFAULT` remains.

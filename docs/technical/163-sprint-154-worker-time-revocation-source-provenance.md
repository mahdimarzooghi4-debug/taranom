# TRN-TECH-163 — Sprint 154: trust-source claims, time provenance and alleged revocation evidence

## Objective
Distinguish **syntactic integrity of claimant-provided time or revocation notice bytes** from **independently authenticated origin**. The predecessor Sprint 153 correctly rejects temporally inconsistent *self-asserted* key expiry/revocation events; it does NOT show whether the named time source or the issuer of a revocation notice is genuine. This sprint builds an explicit **negative-only, synthetic, provider-neutral technical test boundary**. No external time source, independent revocation feed, organization, key, signature format, service account, legal custodian or operator is approved.

## Contract and tests
The public template `docs/governance/ai-worker-time-revocation-source-template.json` has `candidate:null`. Under `tools/qa/worker_time_revocation_provenance_denial.py`, a bounded, allowlisted test-shaped claim has one alleged clock assertion and at most six alleged revocation/retirement notices. Both bear test-only opaque references, exact canonical UTC string time, and an uppercase SHA-256 digest over their own *claimant-controlled* canonical JSON with the synthetic transfer/challenge binding. No provided bytes are dereferenced, no network call is made, and no real clock is read. **The digests are PUBLIC and reproducible by any claimant, NOT signatures or trustworthy source evidence.** Syntactically complete, internally consistent and even fully recomputed altered claims still give only `SOURCE_CLAIMS_REQUIRE_INDEPENDENT_PROVENANCE_REVIEW`; no true signature, source or revocation verification result exists.

The evaluator rejects cross-transfer/challenge replay, byte alteration without recomputed digest, duplicate assertion refs, conflicting revocation/retirement notices on one alleged key, impossible effective/observed order, regressing observation times, a notice observed after the claimed clock time, malformed/naive clock time, unsupported fields posing as signatures/approval, oversized or duplicate-key JSON, and forged prior temporal authority. It accepts its prior context only if the existing Sprint 153 evaluator has a structurally checked synthetic archive and *all* authority flags are false. Output never reflects untrusted sources, key/recipient identifiers, timestamps or raw input. All flags remain **false**, including `clock_source_authenticated`, `revocation_source_authenticated`, `attestation_signature_verified`, `revocation_notice_verified`, `trusted_clock_verified`, `custodian_identity_verified`, `human_release_approved`, `production_ready`, and `national_release_allowed`.

The canonical full 14-job CI runs the new negative tests and invokes the evaluator with the empty checked-in template after an actual Kestrel SIGTERM/restart, .NET→local Python synthetic child read, independent HMAC checkpoint, two-epoch ZIP handoff, and prior negative receipt/identity/lifecycle/temporal gates. Existing PostgreSQL and Chromium regressions, role checks, unprivileged Linux verifier separation and real isolated restore rehearsal stay mandatory.

## Unresolved, explicit HUMAN/EXTERNAL decisions
An actual independent source of time and its approved authentication trust anchor, allowed time semantics/synchronization uncertainty, attested signing/certificate/key and revocation issuer(s), evidence provenance and verification of independent administrative control, receipt/signature canonical format and replay store, expiry/retention/privacy rights, and accountable human authorization/release approval remain OPEN. These are **not invented by code**. A string reference, recomputed digest, syntactically ordered event or signed-looking field cannot decide them.

This work does NOT implement WORM storage, real medical data, patient consent, external AI APIs, model inference/training, real receipt signatures or Production admission. PR stays Draft/Open/Unmerged with ancestors; no Human APPROVE, Ready for Review, Merge, Stage/QA, Release, Production or national deployment. National launch remains `DENIED_BY_DEFAULT`.

# TRN-TECH-177 — DRAFT / exact-journal acknowledgement and read-only recovery for organization activity

Date: 2026-10-18. Existing approved technical source TRN-TECH-135 and organization scope/RLS foundation TRN-TECH-131–134; no new Business approvals or operational authority.

## Real identified gap
The existing local support-organization activity workbench displays the latest audited activity and uses immutable, versioned PostgreSQL records. The browser previously cleared its uncertain-write latch when any synthetic 200/Recorded or Replayed response reported a sufficiently high `currentNo` for the chosen item, even if that response could not prove that the original `requestRef` and `noteRef` were the actual event at `expectedPreviousNo+1`. A wrong or forged success ACK could therefore unlock further writes without command ownership verification.

## Bounded contract and implementation
- Retain the one owner-scoped, RLS-enforced, `CI_EPHEMERAL_ONLY` PostgreSQL organization source and original append-only activity journal. No new API, DTO schema, DB table, login, tenant selection or mutable business status.
- For a `Recorded` or `Replayed` response with previously required valid status, exact case/item, bounded current revision and all deny flags still false: issue one GET of the already existing activity journal. Accept success **only** if that independent trusted read returns `Read` with exactly `currentNo` contiguous events, and **exactly one matching original requestRef at activityNo=expectedPreviousNo+1**, with its `noteRef` and encoded original command fields matching the immutable in-memory original payload. Historical accepted replay may have newer subsequent activities, but the exact original event must remain at its original version. The first reported success is not sufficient by itself.
- While read verification is untrusted, missing, malformed, unavailable or changed, **retain the exact original URL/payload/requestRef in volatile memory**, keep all new commands disabled, and show an uncertain status without an invented approval or repeated POST. Do not infer success from an event count alone.
- Add a distinct deliberate **بررسی فقط‌خواندنی ثبت قبلی** button while uncertain. It reads the original case activity journal with GET only, performs the exact same requestRef/version/noteRef proof, and clears the pending latch ONLY if that exact event is found. If it cannot prove the source, keep the latch and permit only separately clicked exact original replay. Existing stale/conflicting 409 paths still deny the write and require fresh reading.
- Do not persist pending payloads in localStorage, sessionStorage or external services. No verification of real organization, operator, notes or policy is implied. All `organizationAuthenticated`, `operatorAuthorized`, `businessStatusChanged`, `nationalReleaseAllowed` remain false.

## Test evidence and gates
Three new real Chromium + ASP.NET + PostgreSQL scenarios: (1) committed write with lost 200 ACK reconciled via **zero additional POSTs**, journal request+note exact match and immutable denial flags; (2) forged successful POST response with no actual committed event remains uncertain until original POST is explicitly retried; (3) committed write and forged GET with changed note remains locked until genuine read, without extra POST. Keep existing org suite including RLS, cross-scope isolation, stale CAS, replay, audit integrity and original full 14-job regression.

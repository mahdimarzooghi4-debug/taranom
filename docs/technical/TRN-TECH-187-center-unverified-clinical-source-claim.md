# TRN-TECH-187 — DRAFT / Center manual unverified clinical-source reference over existing care journal

Date: 2026-10-20. Business source: TRN-BIZ-046 (hybrid treatment pathway coordination), TRN-BIZ-035/036 (separate actual health-data rights/consent) and TRN-BIZ-043 (professional qualification authority). Technical sources: TRN-TECH-115/184/185/186. This contract is for a **strictly test-only** workflow, not clinical record access.

## Existing domain capability; UI gap
The canonical `SyntheticCareCoordinationTrail` already supports three event types: genesis `RequestNonclinicalCoordination`, follow-up `RecordUnverifiedCoordinatorContact` and follow-up `AttachUnverifiedClinicalSourceReference`. Both follow-up actions are explicitly *claims*, requiring the same already-referenced original request UUID/member/originalRef, a new idempotency UUID and test-only actor/note-or-document reference. Since Sprint 175 the Center QA browser exposed manual contact claim only; the second preexisting domain action required external commands or the Member test UI and was not available as a separately human-chosen Center workflow.

## Implementation
- In existing Center QA's source-backed nonclinical workbench, keep the independent `GET /internal/demo/v1/care-coordination/{caseRef}` read and the new Sprint 177 bounded worklist. After an actual source-verified first member request, show **two independent buttons**: existing contact claim and new **ثبت مستقل مرجع بالینی تأییدنشده**. New action reads an independent bounded `test:` sourceRef input, along with the existing clearly **claimed** actorRef; does not consume the separate contact-note input. No automatic submission or state promotion.
- The new button maps **only** to the preexisting backend action `ATTACH_UNVERIFIED_CLINICAL_SOURCE` and persisted domain enum `AttachUnverifiedClinicalSourceReference`; the original contact button retains `RECORD_UNVERIFIED_COORDINATOR_CONTACT`. A single source-pinned command builder captures the exact original PostgreSQL case/member/root request UUID, expected current revision, fresh UUIDv4, selected action, claimed actorRef and selected source/noteRef. No new API route, schema, domain action, permission, role, external source connector or business policy.
- The original in-memory pending transaction must **include its selected action**. A 200 `RecordedUnverified` or `Replayed` ACK is accepted only if both its exact persisted event **action** and original UUID/version/lineage/actor/ref match, followed by a separate `READ` GET from the existing immutable PostgreSQL journal that verifies the *same* event. A contact event with matching UUID/ref cannot satisfy a source-attachment ACK. Any missing/invalid/forged ACK or stale concurrent revision retains the original bytes and UUID, locks all fresh actions, and allows only separately human-clicked GET-only reconciliation or exact original manual replay. No automatic second POST.
- UI must label the resulting attachment as an **unverified clinical-source claim**; it does not inspect file contents, prove a source, validate professional licence, obtain member consent, read patient records, grant access, perform a referral, schedule a visit, give an emergency alert, or authorize Production. Member's previous test-only independent care timeline can read the unchanged original journal and see the new event, but such visibility is not data-rights proof.
- Existing all-13-denial source validator remains mandatory. No non-`test:` identifiers and no new cross-tenant joins. The event does not modify insurance/finance/provider/member rights.

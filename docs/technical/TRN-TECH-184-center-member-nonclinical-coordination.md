# TRN-TECH-184 — DRAFT / Center and Member share the existing nonclinical coordination source safely

Date: 2026-10-19. Basis: TRN-BIZ-046 hybrid coordination model and existing TRN-TECH-115 care journal. Only synthetic test-only `test:` fixtures. No legal, clinical, patient-data or center-identity approval is implied.

## Real bounded user operation
The member-side nonclinical care coordination workbench already writes an append-only/audit-verified PostgreSQL trail of an initial **unverified member coordination request**, independently claimed coordinator-contact notes and opaque clinical-source references. The Center QA browser previously had no operable view of this existing *separate* journal; after a member submitted a test request the center could not independently inspect and record a human-triggered nonclinical contact claim using the same source. This Sprint joins only those two **CI-ephemeral loopback test workbenches**. In Production such a cross-panel read/write would require verified member/center identity, service-scoped authorization and independent clinical/privacy approvals, none of which exists here.

- Introduce a separate visible Persian `InternalCareCoordination` panel **inside the existing Center QA shell**, which manually inputs an exact synthetic case reference, and reads only the EXISTING `GET /internal/demo/v1/care-coordination/{caseRef}` over loopback same-origin. The source must have a valid original request. Reject incorrect contract/outcome, malformed/missing version, noncontiguous event sequence, duplicate/invalid random UUID, inconsistent member/original-request scope, unknown actions, malformed claimed actor/notes and any of 13 real-authority flags becoming true. No inference from an opaque receipt; no browser-stored token or broad member directory.
- Offer a single explicitly clicked, *existing domain* action `RECORD_UNVERIFIED_COORDINATOR_CONTACT`, with exact previously read revision, root member/request identity, original submission UUID and a fresh UUID for the new command. Actor and note are `test:` references and are unverified claims, never evidence of a delivered call, treatment or professional qualification. Use the original `POST /internal/demo/v1/care-coordination/{caseRef}/commands` without changing API, domain enum, database or role privileges.
- A successful POST/ACK does **not** unlock the next command unless it matches the exact original request UUID, version, member/root identity, action, actor and note **and** a separate GET from the canonical PostgreSQL source confirms the same event at the original version. On a lost/forged/invalid reply, retain the original byte-for-byte request URL/body/UUID in volatile component state, block all new writes, and offer two distinct human clicks: (a) **GET-only** original-event reconciliation, or (b) replay exact original payload/UUID. Never automatically submit again or replace the UUID; a missing or mismatched original event keeps the latch and fails closed.
- Member browser continues to use its *existing* independent care reader; after the center's accepted unverified contact, it can see the exact same journal revision and claim. It is not a medical record share, a verified clinic/referral, or a member notification. No cookies, storage, IdP stub, cross-context foreign key, new endpoints or real patient records.
- No new urgency evaluation, contact SLA, care prioritization, source authenticity, health-data consent, referral completion, automatic model recommendation or human-vs-AI authority is defined or invented.

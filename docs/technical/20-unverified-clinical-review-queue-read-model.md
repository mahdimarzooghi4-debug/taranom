# TRN-TECH-020 — Center-scoped unverified evidence review queue, read-only

**Status:** Internal synthetic-only implemented read model, not a live reviewer panel, reviewer authorization or decision workflow. Business references TRN-BIZ-053/054 (a center with many departments, no independent network administrator), TRN-BIZ-043/044 and Technical TRN-TECH-018/019 (claim != qualification/contract confirmation).

## Meaningful new capability
A separate `PgUnverifiedEvidenceReviewQueue` class in the existing **test-only** `Taranom.ClinicalEvidenceJournal.Postgres` project provides an internal, one-center **list of unverified submitted evidence and associated review work items**. It can distinguish a center representative's claimed management delegation from a physician's qualification claim and a distinct Taranom service contract claim. It never activates either.

- Source: accepted review events joined to one pending-review work item, paired accepted audit and scoped case in **isolated PostgreSQL 18**. No real documents, names, national IDs, health data, contracts, qualified actors, grants or human decisions are present.
- Filter: one explicit synthetic `test:` center; optional physician vs representative subject category. All queries enforce `e.center_ref=@center`, and no network parent/cross-center union exists. **This center string is not an authenticated principal or source-backed center ownership proof.** No user, reviewer, panel, API, endpoint or runtime service can call this as a permitted real query.
- Page: keyset ordering `(subject_ref COLLATE "C", subject_kind, event_revision)` with a typed cursor binding the center and filter. Input rejects malformed center/cursor/type and non-positive or oversized technical page sizes; returns only `UnverifiedReviewQueueItem` metadata and optional continuation. Cursors are **test-only, unsigned, caller-supplied**, not a trusted/signed external pagination contract.
- Data-integrity checks: for every row returned by this page, require paired review work item, paired accepted audit, SHA-256 digest, exact claimant/ref/kind/revision/center match and case revision not behind the accepted event. Raise on inconsistency. This is a **per-returned-row** integrity check; it is not a full-case replay of all event history or a tamper-proof external audit, and a PostgreSQL owner can change its tables.
- Least privilege: queue tests use a separate ephemeral PostgreSQL **SELECT-only** database principal, and prove UPDATE/DELETE is rejected. A separate owner connection is used only for synthetic seeding and tampering tests, never as the queue reader's permission source.
- Keyset paging is **not a consistent snapshot across multiple page calls**. Newly committed review claims may appear if their sort key is after the cursor; records inserted before a cursor can be omitted from that traversal. Do not advertise stable exhaustive review or fair assignment until explicit snapshot/time semantics are designed and verified. No review decision or queue completion state exists.

## Security and product boundaries
No real center representative Identity Provider, human reviewer access policy, center tenancy registry, professional medical regulator, signed contracts, source validation, privacy consent, legal data-retention, evidence documents or eligibility decision exists. A `test:` ref is not authority. The earlier protected-data Interlock **remains deny-only**, the web center panel remains disconnected, and no operational API or doctor activation is introduced. The queue is purely a technical way to inspect synthetic pending-review cases after they are committed, not a new staff role or mandatory reviewer portal. Do not infer a confirmed clinician from the existence of a case.

# TRN-TECH-192 — DRAFT / Manual same-page coordination worklist change inspection
2026-10-21. Business TRN-BIZ-046; existing governed technical TRN-TECH-115/172/186/190/191. Only anonymous, synthetic `test:` Center QA; no patient directory, member identity or actual care.

## Operational goal and bounded design

Sprint 182 can source-filter and paginate cases by existence of unverified contact/clinical-reference claims, but once a Center reviewer opens a page it cannot identify which of **these same four displayed cases** received additional claims through the shared Member/Center PostgreSQL journal. Comparing all counts visually is manual error-prone. Introduce explicit **human-clicked re-read of the exact same page** and a factual per-case delta of newly appended, unverified *claim counts* (contact vs clinical-source) since the previous source-backed read. No change to the backend or business domain.

The new refresh repeats the SAME existing `TRN-TECH-186` worklist GET with exact `afterCaseRef`, `limit=4`, `claimFilter`, which is already fully reattested by least-privileged, REPEATABLE READ / READ ONLY PostgreSQL event+audit canonical replay. Existing browser response contract, count/revision invariants and all 13 authority denials must pass. The comparison rejects any changed page membership or order, changed next cursor / pagination boundary, reduced revision/contact/source count, or inconsistency between revision increase and claim-count increases. On disagreement, stale/forged input or HTTP error, clear old rows, activity and selection controls and fail closed. A fresh normal manual read is needed to establish a new baseline; never silently rebase the comparison after a keyset insertion. If no change, display zero. If source-backed counts grew, display exact caseRef, resulting version and separate positive contact/source increments. A POST and its ACK are never interpreted as proof of an activity refresh.

Changing filter/cursor, choosing next page, returning to initial read or an uncertain external request invalidates earlier activity. No automatic poll, notification/read/unread state, SLA, triage, missing-contact task assignment, appointment, clinician or treatment inference, new endpoint, persistent storage, new schema, role or domain action. Selecting a case still only fills its ref, requiring the existing separate verified GET and manual write path.

## Acceptance

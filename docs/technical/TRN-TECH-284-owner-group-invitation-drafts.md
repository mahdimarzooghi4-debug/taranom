# Owner-scoped group invitation drafts

Implements persisted planning drafts for group invitations, not active group membership or an invitation delivery service. Existing Figma method chooser 100:73 and list-card patterns from 100:2 are reused for `/patient-app/add-member` and `/patient-app/group-members` (also `/patient-app/group`). Existing local logo, bell and account-active navigation assets are exact matches. The recipient-label form, receipt, archive control and draft-only wording are functional additions, not an existing Figma form.

Business boundary: people register independently and must accept their own invitation. Payer/organizer status does not transfer membership/wallet ownership or permit medical access (TRN-BIZ-029/035 and supplied group flow). Real recipient resolution, delivery, acceptance, guardian/minor rules, identity verification, pricing, payment and activation remain separate unfinished work. This increment does not invent a phone-directory provider, send SMS/email, find an account by name, link a recipient subject, or create a grant/notification/clinical record.

The only recipient field is an owner-entered label (2–100 characters), explicitly unverified local planning data. Method is NewRegistration or ExistingMember. Strict JSON input rejects recipientSubject, identity, accepted-state and other authority selectors. A Draft cannot be considered sent, accepted or an active member. Existing membership row in All Services remains unavailable; a separately named draft link is added in the expandable account section and account card.

GET `/api/v1/me/group-invitation-drafts?requestId=&draftRef=&before=` returns at most 20 owner issuer/subject rows and a server cursor. POST creates a Draft with a unique owner/requestId receipt and normalized payload fingerprint; concurrent exact retry replays, altered payload conflicts. POST `/{draftRef}/withdraw` monotonically archives it, preserving the first withdrawal timestamp on repeats. Create replay returns the current archived state and cannot resurrect a draft. API data is no-store; cross-owner archive is 404. There is no participant data exchange.

The UI shows explicit draft status, never sample relatives, ages, fees or accepted group members. Uncertain create/archive responses reconcile through an exact owner GET without repeating POST. Archive has in-page confirmation. Refresh/denial clears stale data. No browser storage or new authentication bypass is introduced. New table/index follow the existing locked PostgreSQL bootstrap pattern.

Validation: member build/typecheck and browser cases for persisted draft/reload, lost create/archive receipts, confirmation, missing session/no traffic, denied refresh, malformed receipt, connected catalog compatibility and 390px local asset geometry. PostgreSQL HTTP cases cover owner/anonymous isolation, no new appointment authority/profile/member notification, concurrent retry/conflict, monotonic withdrawal/replay, strict selectors and bounded nonoverlapping pages. APK, deployment and merge remain deferred.

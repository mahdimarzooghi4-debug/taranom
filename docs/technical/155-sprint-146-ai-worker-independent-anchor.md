# TRN-TECH-155 — Sprint 146: verifier-side anchored synthetic Worker history

## Boundary and technical objective
Sprint 145 added a bounded, process-local SHA-256 linked synthetic evidence file. A compromised local file owner can rewrite **every** entry and recompute all unkeyed hashes without detection by the file-only verifier. This sprint adds a deliberately **test-only verifier-side checkpoint** that anchors the sequence, prior head digest and complete observed byte-prefix digest *before* the real Kestrel process restart. It verifies the same protected prefix and new Boot→Success continuation *after* restart.

Only an independent Python command (outside Kestrel and its child worker code) generates a fresh verifier HMAC secret and a canonical, fixed-field checkpoint in a second disposable `/tmp/taranom-anchor-*/` directory. CI creates it with mode 0700; verifier files are mode 0600, single-link, no symlinks. The secret and directory are never set as exported host/child-process variables or transmitted through HTTP, model inference, clinical data, or logs. Checkpoints are create-once and cannot be silently replaced; any missing secret, malformed manifest, modified MAC, altered anchored prefix, truncated history, replayed epoch or missing post-restart success fails closed with no automatic re-anchoring or fake acceptance.

The new `tests/ai/test_worker_evidence_anchor.py` is included by existing mandatory AI test discovery. It simulates **complete recomputation of all public SHA-256 links** after changing an earlier legitimate record: the plain ledger verifier still accepts the rewritten chain, while the verifier-held checkpoint correctly rejects it. The tests also check truncation, tampered or missing verifier key/manifest, wrong anchor location, symlink, file permissions and flags. In the unchanged 14-job full regression, the real Chromium/PostgreSQL Kestrel test creates this checkpoint after all initial HTTP/browser tests; the existing SIGTERM, real host restart, resumed one-shot Python read, non-identifying counter discontinuity test and independent SHA-256 ledger verifier then run unchanged; an extra verifier command checks exact persisted pre-restart history and Boot→Success continuation against its pre-restart checkpoint.

## Explicit security limits
This is **not independent legal custody, authenticated regulatory audit, external WORM storage or tamper-proof evidence**: both Python verifier and .NET host are on the **same CI runner and same OS owner**. An attacker with that account, access to the verifier key, or ability to replace code/CI can forge a new checkpoint. The ephemeral HMAC is unrelated to approved service identity, training authority, patient consent or Production credential management. A successful run is technical synthetic negative-test evidence only, not continuity/SLA attestation, real-world uptime, approved backup recovery, or a model/human promotion gate.

Nothing enables AI training, real clinical/finance data, network AI APIs, real IdP, operational AI decisions or model activation.
